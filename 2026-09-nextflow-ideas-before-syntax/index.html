Nextflow

The ideas before the syntax

Channels, processes, operators and tasks. A preamble while your codespaces load.

One tool, from a laptop to a pharma fleet

The same pipeline serves a single researcher and the largest biotech organisations

For a researcher
●Write the science in whatever language it is already in. Bash, Python, R, a container. Nextflow wires the steps together.
●Develop iteratively. Change one step and re-run; everything that already worked is reused, not recomputed.
●Tight git integration. Run a stable, tagged analysis while trying out new ideas on a branch.
●Metadata travels with the data. Write steps that never have to guess how a file name is constructed.
For an organisation
●Portable across infrastructure. One pipeline runs on every team's compute, so there is one RNA-seq pipeline, not ten. Teams collaborate instead of duplicating.
●Provenance for every output. Each result is traceable to the exact inputs, parameters and code that produced it.
●Scale by adding samples, not engineers. One sample and ten thousand samples are the same pipeline.
●A shared vocabulary. New hires, collaborators and vendors already speak it.

Channels

Data and its metadata, travelling together

A directory of files and a script

Metadata lives in file names and paths, and the script has to parse it back out

sample=$(basename $f | cut -d_ -f3)
ref=$(basename $f | cut -d_ -f4)
call_variants $f $sample $ref
done

●Which reference was sampleC aligned to, and by whom?

A channel keeps metadata beside the data

Each item is one sample: a metadata record, then the files that belong to it

samples

ref: hg38
A_1.fq.gz

id: B
ref: hg38

B_2.fq.gz
id: C
ref: hg38
C_1.fq.gz
C_2.fq.gz
●Metadata is a record, not a file name. The hatched cell holds it. Nothing is parsed; nothing is guessed.
●Samples are isolated. Each item is its own row. A step working on A never sees B.
●A channel is a queue. Items enter at the top and leave at the bottom in order, so downstream work starts as soon as the first item arrives.

Operators

Reshaping channels without running a script

Tasks

One process, many isolated executions

Every item spawns its own task

Tasks run in isolation, in their own work directories, and finish as soon as they are done.

For a researcher

Polyglot · Iterative · Versioned · Metadata-aware

Write the science in the language it is already in

Each process wraps one script; the pipeline does not care which language

counts.to_csv("${meta.id}.csv")
Python
DESEQ

R
●Existing scripts become processes with almost no change. The tool you trust stays the tool you run.
●Each process brings its own container or conda environment, so R and Python dependencies never collide.

Change one step and re-run only that step

Finished work is cached; an edit re-runs the edited process and whatever depends on it

Nextflow ♥

A pipeline can be a git repository; every run knows which revision was used

Stable
$ nextflow run acme-rx/rnaseq -r v2.3.0
Pinned to a tag. Every sample this quarter goes through exactly this code.
Experimental
$ nextflow run acme-rx/rnaseq -r try-salmon
A branch. Same repository, same samples, a different aligner. Merge it when it earns its place.
●No copies of the pipeline on disk to drift apart. The repository is the pipeline.
●The run log records the commit, so any result can be traced to the exact code that produced it.

Processes never guess how a file name is built

The script reads metadata from the item, not from the path

id: A
ref: hg38
strand: reverse
L001_R1.fq.gz
L001_R2.fq.gz
process ALIGN {
input: tuple val(meta), path(reads)
script:
"""
star --id ${meta.id} \
--strand ${meta.strand} \
--genome ${meta.ref} ${reads}
"""
}
●A name is not a contract. One underscore in a sample ID, a renamed file, a new sequencer convention, and the parsing silently returns the wrong field.
●Add a field to the metadata and every downstream process can use it, with no renaming.

06

For an organisation

Portable · Scalable · Traceable · Shared

One RNA-seq pipeline, not ten

The pipeline describes the work; a profile describes the machines

acme-rx/rnaseq
one repository
-profile laptoplocal · docker
-profile hpcslurm · singularity
-profile awsbatch · s3
●Teams on different infrastructure contribute to the same pipeline instead of maintaining parallel copies.
●Moving compute, to a new cluster or to the cloud, is a config change, not a rewrite.
●Containers travel with the pipeline, so the software is the same everywhere it runs.

Just add data

One sample and ten thousand samples are the same pipeline; only the number of tasks changes

●Tasks are scheduled onto whatever compute the profile offers; parallelism is free, not designed in.
●A failing task retries or fails alone. The other 9 999 carry on.

Every output traces back to what produced it

Result → task → inputs, parameters, script, commit

A.bam

inputsA_*.fq.gz · hg38.idx

●The chain is recorded as a side effect of running, not assembled afterwards by hand.
●Reproducing a result means re-running the same commit with the same inputs. Nothing else to remember.
●The same record is what lets a run be resumed, so provenance and efficiency come from one mechanism.
